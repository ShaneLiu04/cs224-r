## 1. Countdown：停止符漏了一种 BPE

**20 秒**：`</answer>` 前面有没有空格，BPE 切出来的 token id 不同。停止序列只登记了一种，生成越过答案标签。两种 id 都截断之后，生成停在标签上，但 120 步 RLOO 的 pass@8 仍是 0.340，没有稳定超过 SFT。

- **S**：Qwen2.5-0.5B，Countdown。第一批 RLOO 的格式奖励和精确匹配对不上，样本在 `</answer>` 之后还在生成。
- **T**：不改奖励函数，找出越界原因。
- **A**：把生成结果按 token id 打出来，对照 tokenizer。带前导空格和不带前导空格是两个 id。停止序列改成两个都接受，损失在闭合标签处截断，标签后面的 token 不进策略梯度。
- **R**：修正后的短程运行（每步 4 个提示）里，40 步 pass@8 为 0.420，120 步为 0.340。SFT 的 pass@1 是 0.188。短程 RL 没有稳定超过 SFT。另一次实验从长 think SFT 出发，留出集 pass@1 从 0.24 到 0.505，pass@4 从 0.445 到 0.60。这是更长的训练和不同的起点，不是这次 bug 修复的结果。
- **白板**：无偏 pass@k = `1 − C(n−c, k) / C(n, k)`。n 是每题样本数，c 是其中正确的条数。
- **不能推出**：不能说「修好停止符之后 pass@1 从 0.24 到 0.50」。0.24 是长 think SFT 的起点，0.188 才是短 SFT。两次实验的检查点和步数都不同。
- **追问**：为什么不用字符串匹配来停？采样引擎按 token 判停。字符串要先 decode 再回扫，批量更贵，而且和损失掩码用的不是同一套边界。

## 2. 同卡训练和 vLLM 抢显存

**20 秒**：RL 训练把 caching allocator 留在大约 89 GB。vLLM 启动时按 `gpu_memory_utilization × 整卡显存` 申请，不看别的进程还剩多少，所以同卡初始化失败。训练和评测改成一条队列，评测 utilization 设为 0.3。

- **S**：单卡上要放策略、参考模型、AdamW 状态，评测还要再起一个 vLLM。
- **T**：不减小组大小，让训练跑满，评测也能跑。
- **A**：训练侧把词表上的 log-sum-exp 放到 float32 并按时间分块，注意力用 scaled dot-product，不物化 `[B, H, T, T]`。推理侧确认 89 GB 是训练进程的缓存而不是 KV cache（0.5B 的 KV 在这个长度上只有几十 MB 量级）。`empty_cache()` 只作用于调用它的进程。于是评测不和训练并行。
- **R**：长程步时 22–35 秒，GPU 利用率接近 100%，没有 OOM。
- **白板**：0.5B、AdamW、bf16 训练。`N = 5×10^8`。bf16 权重 `2N` = 1 GB，fp32 主权重 `4N` = 2 GB，一阶矩、二阶矩各 2 GB，bf16 梯度 1 GB，合计 8 GB。参考模型只有 1 GB 权重。激活和 logits 另算，见 [ENGINEERING §3](ENGINEERING.md#3-显存账)。
- **不能推出**：不能把 89 GB 说成 KV cache 或模型权重。权重加优化器大约 9 GB，其余是激活、logits 和分配器碎片。
- **追问**：为什么不在另一个进程里 `empty_cache()`？缓存属于持有它的进程，别的进程释放不了。

## 3. 用恒等式检查 IPO，而不是看损失下降

**20 秒**：策略等于参考策略时 IPO 损失必须是 `(1/(2β))²`。β=0.1 时就是 25。第一步实测是 25，DPO 是 0.693，也就是 `log 2`。之后求和版验证损失升到 31.07，长度平均停在 25.01，偏好准确率都在 0.5 附近。

- **S**：IPO / DPO 的损失曲线可以在实现是错的时候仍然下降。
- **T**：找一个不需要训练收敛的检查。
- **A**：`π = π_ref` 时 `Δ_w = Δ_l = 0`。IPO 变成 `(0 − 1/(2β))²`，DPO 变成 `−log σ(0) = log 2`。写成单元测试，另外覆盖 SFT 标签右移、提示不反传、RLOO 优势。
- **R**：恒等式对上了。长度平均把验证损失留在恒等式附近，求和版漂到 31.07。准确率没有离开 0.5，所以损失下降不能单独当成对齐完成。
- **白板**：`L_IPO = (Δ_w − Δ_l − 1/(2β))²`，`Δ = log π_θ − log π_ref`。
- **不能推出**：准确率停在 0.5 不能单独证明损失函数写错。恒等式已经通过，剩下的是数据或序列聚合方式的问题。
- **追问**：为什么求和更不稳？两条回答长度不同，`Δ` 的量级不同，平方损失被长回答主导。

## 4. CQL 的「探索数据」是最短路贪心

**20 秒**：`--use_rnd` 几乎不改变结果，因为 `step_env` 在两种设置下都调用 `get_optimal_action`，也就是全源最短路上的一步贪心。这个开关只改 `learning_starts`。我加了 `--behavior explore`，默认仍是原来的 oracle。

- **S**：作业要求比较 RND 探索和随机探索收集的数据。
- **T**：解释为什么开关不起作用。
- **A**：读 `explore_or_exploit_agent.step_env`。新增 `--behavior {oracle, explore}`，oracle 保持原行为。另外用 oracle 策略做了评估基线。
- **R**：oracle 数据、Medium 迷宫、α=0：全部种子 −150（失败）。α≥0.01 能解。OOD gap 从 α=0 的 1.91 降到 α=3 的 0.12。换成真实探索数据后，IQL 和 CQL 的排序反过来，见故事 5。
- **白板**：离散 CQL 惩罚 `α (logsumexp_a Q(s,a) − Q(s, a_data))`。α=0 时没有这项，OOD 动作的 Q 可以高于数据动作。
- **不能推出**：不能说作业原本的 RND 实验比较了两种探索。那些曲线比较的是同一个专家数据集上的 α。
- **追问**：怎么排除是自己改坏的？固定种子，比较两个开关写下的动作序列。动作序列相同，才把原因归到 starter。

## 5. 同一环境，IQL 和 CQL 要的数据相反

**20 秒**：Medium 迷宫上，IQL（ζ=0.7）用 RND 数据是 −50.85±2.43，用随机数据是 −90.69±6.72。CQL（α=0.1，6 个种子）用随机数据是 −34.3±6.1，用 RND 数据是 −67.6±26.9；RND 数据上把 α 加到 1，全部种子 −150。

- **S**：同一个迷宫，离线数据分别来自 RND 策略和 ε-随机策略。
- **T**：看覆盖更好的数据是不是对两种算法都更好。
- **A**：IQL 扫 ζ，CQL 扫 α，每种至少 3 个种子，离群的设置补到 6 个。
- **R**：上表。我的解释是 RND 数据铺得开，但每个状态上的动作更少；CQL 把数据外动作压低之后，策略被留在这些稀少的数据动作上。这是对 α 扫描的解释。我没有单独统计每个状态的动作熵，所以面试里我会把它说成解释，不说成测量。
- **白板**：IQL 的 V 损失是 expectile，`|ζ − 1{Q−V < 0}| (Q−V)²`，只在数据动作的 Q 上回归，不查询别的动作。
- **不能推出**：不能说「RND 数据质量更差」。IQL 在这份数据上更好。数据没有绝对的好坏，要看算法怎么用它。
- **追问**：为什么 α 越大 RND 数据越差，oracle 数据却一直能解？oracle 数据里好动作重复出现，压低其余动作正好把策略留在好动作上。RND 数据里留下的动作本身不一定好。

## 6. HER：25-bit 从 0 到 1

**20 秒**：bit-flip 奖励是 0 或 −1。无 hindsight 时 15-bit 和 25-bit 成功率都是 0，6-bit 是 0.896±0.143。final、future、random 三种重标记最终都到 1.0。

- **S**：目标随机，DQN 几乎采不到奖励为 0 的转移。
- **T**：实现三种重标记，并看 k 和奖励密度的影响。
- **A**：每条转移额外写入 k 条，把目标换成后来实际到达的状态。Q 目标裁到 `[−1/(1−γ), 0]`，γ=0.98。
- **R**：25-bit 到成功率 0.9 用了 290–320 个 epoch。k ∈ {1, 2, 4, 8} 在 15-bit 上没有差别（90–95 epoch）。Sawyer 是稠密奖励、5 个种子：无 hindsight 0.547±0.106，random 重标记 0.994±0.006。
- **白板**：原转移 `(s, a, s', g)` 失败。取后来到达的 `g' = s_{t+k}`，写入 `(s, a, s', g')`，这条在新目标下是成功的。
- **不能推出**：k 在 15-bit 上没差别，不能说 k 不重要。25-bit 没有扫 k。Sawyer 上 random 最好，也不能外推到所有机器人任务。
- **追问**：什么时候有偏？环境随机时，到达 `s'` 的转移是在原目标条件下发生的，换成新目标后转移分布变了。确定性环境里 future 策略没有这个问题。

## 7. DREAM 和 RL²

**20 秒**：网格上走路回报 0.1，读地图再坐公交是 0.7。DREAM 0.696±0.007（5 个种子），RL² 0.143±0.073。把每步探索代价 c 设为 0，回报仍是 0.70，探索长度升到 9.9±0.16，顶到回合上限。

- **S**：任务是「地图在哪」。信息有用，但探索的收益出现在后面的回合。
- **T**：比较端到端的 RL² 和把探索、利用分开学的 DREAM。
- **A**：DREAM 用解码器拟合探索轨迹里的任务信息，探索奖励是信息增益减去 c。c 的默认值是 0.1，另跑 c=0。
- **R**：DREAM 接近 0.7，RL² 接近走路的 0.1。c 改变的是探索长度，不是最终回报。c=0 只有 3 个种子。
- **白板**：最优 0.7 来自地图格 (4,2)，中心是 (2,2)，相距两步。先读地图再坐公交，而不是一直走。
- **不能推出**：回报顶在 0.7，不能说 c 对策略没有影响。它把探索长度从几步拉到接近上限。RL² 的失败也不能说成 RNN 一定学不会，只能说在这个信用分配长度上它没学会。
- **追问**：RL² 的信用分配卡在哪里？探索发生在这个回合，奖励体现在下一个回合的隐状态里，策略梯度要穿过整段历史。

## 8. 上游包下线、数据集被截断

**20 秒**：HW2 依赖的 MuJoCo 2.1 安装包已经下线，HW3 公开的 `antmaze-medium-diverse-v0` HDF5 是截断的。我换了当前的 mujoco 和 Meta-World，数据集改用修好的 v2，观测、动作、成功判定和 action repeat 保持作业定义，并写进报告。

- **S**：starter 的安装步骤和数据链接不能原样跑通。
- **T**：让实验可复现，同时不把任务定义改掉。
- **A**：`mw.py` 同时接受 `step` 的四元组和五元组返回。20 条 hammer 示范从官方 upstream zip 恢复，不重新采集。HW3 改用 v2 文件，报告里写明没有用 v0。
- **R**：多种子曲线和两份报告都跑完了。和旧版数字对比时，差异来自数据文件和物理库，不是来自算法。
- **不能推出**：不能说这些数字可以直接和用 MuJoCo 2.1、v0 数据的论文表格对齐。
- **追问**：怎么证明任务没有被改掉？核对观测维度、动作范围、success 的定义和每步 repeat 次数，而不是只看回报曲线长得像。

## 9. 多种子统计先在种子内聚合

**20 秒**：不同种子的评估步数不一样。把它们拼成一张表再取「最后几行」会取到别的种子的空位，均值变成 NaN。改成每个种子先取自己的尾部均值，再跨种子算 mean±std。

- **S**：CPU 上并行跑几十个种子，步数和结束时间都不齐。GPU 按小时计费，同一张卡还要跑 LLM RL。
- **T**：让统计口径固定，并且卡不空转。
- **A**：GPU 用文件队列，脚本按文件名排序，`.sh` 开始后改名为 `.running`，结束进 `done/`。CPU 核并行跑小环境的种子。绘图脚本只读 CSV / JSONL，写出图和 LaTeX 宏。
- **R**：报告里的数字都可以从原始文件重新生成。NaN 的那次是聚合顺序的 bug，不是训练崩了。
- **不能推出**：队列本身不提高样本效率。它解决的是计费和可复现，不解决算法问题。
- **追问**：为什么不直接 `dropna` 之后取全局最后几行？那几行可能全是跑得最久的一个种子，其余种子被丢掉，方差会被低估。
